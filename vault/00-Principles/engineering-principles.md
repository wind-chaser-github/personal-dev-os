# Engineering Principles

- Start from user outcome and failure modes, not implementation shape.
- Prefer existing project patterns before adding abstractions.
- Keep ownership boundaries explicit.
- Make behavior verifiable with the smallest useful proof.
- Treat tests as claims about behavior, not as coverage decoration.
- Prefer simple rollback paths for risky changes.
- Record durable decisions and rejected alternatives.
- Capture lessons only when they are reusable.
- Comments should explain intent, constraints, and tradeoffs; code should explain ordinary mechanics.
- Review correctness, standards, verification, and maintainability as separate concerns.
- Match verification depth to risk, not to how easy the command is to run.
